Harness Engineering

让 Agent 稳定完成任务。

来源说明 ↓

把目标、信息、行动、验证和修复，组织成一套能持续运行的执行闭环。

模型提供理解与生成能力，外围系统负责工具、状态、反馈和运行边界。可靠交付需要二者配合：既能推进任务，也能发现偏差、恢复执行，并按明确标准结束。

三个概念，各解决一个问题

Prompt、Context、Harness 的工程关注点
关注点要解决的问题
Prompt指令任务怎么讲清楚目标、约束、输出要求。
Context上下文信息怎么给对相关事实、工具结果、当前进度。
Harness执行系统任务怎么可靠完成安排执行、校验结果、处理失败。

按视频的理解框架，指令属于上下文，上下文管理属于 Harness 的执行系统，关注范围逐步扩大。

指令不能代替缺失的事实；信息给对了，执行仍可能跑偏，需要持续验证与纠偏。

三个工程关注点

信息与状态
按需读取相关资料，分开组织规则与任务材料。Skills 先提供能力名称与简介，触发后再读取流程、参数和脚本。任务进度、会话中间结论、长期记忆与用户偏好分开保存；续接时保留待解决问题和证据位置。
执行与工具
把目标拆成可检查的小任务。工具要明确三件事：提供哪些、何时调用、结果如何筛选后送回模型。输入与权限边界要清楚；失败时指出参数、权限或临时故障等具体原因。
验证与恢复
自己实现后再给自己打分容易偏乐观。明确需求规格、实现与验收的职责分工，用测试、实际页面操作、日志或业务结果验收。将失败证据送回下一轮；必要时重试、换路径或恢复到稳定状态，并设置停止条件。

由视频的六层框架合并整理，用于理解机制与排查缺口。

执行闭环：每一步都有完成依据

验证与反馈实践 ↗

示例：修复登录失败

说明性推演
验收
正确密码能登录，错误密码被拒绝，原有权限检查继续生效。
执行
读取认证代码、错误日志与相关测试；复现问题后修改。
反馈
运行针对性测试与相关回归，实际操作页面。失败时提供输入、预期、实际结果和日志，修复后再次验证。

从最小可用流程开始

先选一组真实任务，明确完成标准，记录完成率、人工接管率、耗时和成本。优先补齐最常见的失败环节，每次改动用相同任务与相近预算比较，再用新任务检验。

短任务采用清楚的指令、必要工具和直接验收。长任务再增加状态交接、独立评估与恢复机制；模型或任务变化后，重新检查这些机制的收益。

长任务的上下文。上下文接近上限时，部分模型会丢细节或提前收尾。可用 Context Compaction 压缩历史，在原会话中继续。

如果压缩后仍不稳定，可尝试 Context Reset：保存任务进度、关键结论、证据与下一步，交给干净的新上下文继续。是否重置，应根据模型表现与任务需要判断。

失败时，先定位缺少的信息、工具、状态或检查，再补齐对应能力。
